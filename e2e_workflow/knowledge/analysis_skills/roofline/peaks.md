# Hardware peaks — roofline denominators

**Generated documentation, not a source.** Every number below is rendered from
`perf_knowledge/hardware/data/sku.json` — GEAK's single per-SKU peak table — by
`kernel_workflow/scripts/kernel_tools/extract_sku.py --sync-docs`. `roofline_tools.py` reads the
json directly (`load_peaks` / `resolve_peaks`); this page exists so an agent executing the skill by
hand reads the same numbers. To change a peak: edit `sku.json` (with its `source`), run
`extract_sku.py --check && extract_sku.py --sync-docs`, then the tests
(`e2e_workflow/scripts/tests/test_roofline_skill.py` asserts this page matches the json).

## Selection rule

1. If the structured identity has a product key (`scripts/gpu_identity.py` → `sku` first:
   `mi355x`, `mi350x`, `mi300x`, `mi325x`, `mi308x`, `r9700`; else `target`, which is only ever
   `r9700` | `unknown`), use the block with that `product:` whose `gfx` matches.
2. Otherwise use the block flagged `default_for_gfx: true` for the running `gfx`
   (gfx950 → MI355X, gfx942 → MI300X, gfx1151 → AI_MAX_395). A bare gfx950 therefore gets the
   **MI355X** peaks; an MI350X only gets its own (lower, 2.3 PF) peaks when identity reports
   `mi350x`.
3. **Client RDNA4 peaks are R9700-only.** `gfx1201` has no default block: a bare `gfx1201` lookup
   without `product: r9700` must not inherit these numbers — several SKUs share that ISA — and any
   `gfx120x` with no block is a hard unknown (never derived). `gfx1250` is CDNA5, not RDNA4.
4. Rows `sku.json` marks `geak_support: unsupported` (gfx1100, gfx1200) are kept there for
   reference only and never appear here.

## What the numbers mean

Peaks are **dense, no-sparsity** figures: matrix-engine rates (MFMA on CDNA, WMMA on RDNA; `fp32`
on RDNA is the dual-issue VALU rate). Memory bandwidth is the **datasheet pin rate** even where
`sku.json` stores a measured ceiling (gfx1151: 0.212 TB/s measured vs 0.256 pin) — this skill
ranks, and its `target_eff` priors in `SKILL.md` are op-class implementation priors, not a measured
product derate. The measured R9700 streaming override is in `SKILL.md` and selected by
`target_eff_for`. Do not pre-derate the numbers here, and never put sparse (2:4) rates in `flops`.

Every `% of roofline` computed against these numbers carries `denominator_basis: datasheet` and may
**rank only**; gating or closing a kernel needs a counters numerator over a probed/calibrated
denominator (`perf_knowledge/profiling/roofline_on_mi.md`). A dtype with no `flops` entry has **no
compute peak**: `compute_util` is `None` (unknown), never 0 and never the fp16 rate.

**Compute peaks need validation; the memory axis is the trustworthy one.** BF16 and FP16 run at the
same rate on the matrix core of every part below, so the two `flops` entries in each block must be
**equal** — that equality is the check to keep (it is asserted). Empirical matrix-core
microbenchmarks (e.g. from rocprof-compute) frequently report a BF16 peak ~2× low, which inflates
any BF16 compute-axis `roofline_pct` (sometimes above 100%, where `SKILL.md` §6 L3 flags it
`suspect`). At decode, prefer `hbm_util` and only rank on a compute-axis number once its dtype peak
has been validated against this equality.

Ridges are not stored: ridge = `flops[dtype] / hbm_bw_bytes_s`, a different number for every dtype
(MI355X: ~312 FLOP/B at bf16, ~1250 at fp4; R9700 ~298 at bf16).

## Notes the table cannot carry

- **R9700** (Navi 48, gfx1201, 300 W): `cu` is the physical CU count from rocminfo (64), not the
  PyTorch WGP count (32). There is **no** `fp4` key: this SKU has no block-scaled MX path. A
  repeatedly reused working set that fits the 64 MB Infinity Cache can report effective bandwidth
  above 640 GB/s; do not call that impossible GDDR bandwidth — measure the external-memory roof
  with a streaming working set larger than the cache.
- **gfx1151** (Radeon 8060S, Strix Halo APU): memory is LPDDR5X-8000 on a 256-bit bus (pin rate,
  NOT HBM). Compute is derived from the published 2.9 GHz clock × 40 CU (WMMA 512 ops/clk/CU →
  59.4; dual-issue fp32 256 FLOP/clk/CU → 29.7). `sku.json` carries the measured 212 GB/s
  (`rocm_bandwidth_test`) and 36.9 TF hipBLASLt BF16 GEMM as `measured_ceilings`.
- **MI350X vs MI355X**: same gfx950 silicon, different clocks (2200 vs 2400 MHz) and peaks — never
  copy one into the other.

## Unknown gfx — derived fallback (confidence: low)

If the running `gfx` has no block above, DERIVE from `torch.cuda.get_device_properties(0)` and mark
`peaks.source="derived"`, `peaks.confidence="low"`, `denominator_basis="derived"`:

```
hbm_bw_bytes_s ≈ memory_clock_rate_hz × (memory_bus_width_bits / 8) × 2     # DDR
flops[dtype]   ≈ multi_processor_count × clock_rate_hz × mfma_flops_per_cycle_per_cu[dtype]
```

The derived bandwidth is **frequently wrong for HBM3/3E** — the reported memory clock often understates
the effective pin rate (on gfx950 it derives ~4.1 TB/s against a real ~8 TB/s). Treat any derived-peak
result as `confidence: low`, which per `SKILL.md` means **display only, do not rank on it**.
