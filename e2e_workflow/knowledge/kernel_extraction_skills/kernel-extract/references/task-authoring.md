# Author a self-contained task

The agent authors task-specific code; the skill supplies the shared measurement,
overlay and UT-driver primitives. This is not a prebuilt implementation for every
kernel. Use the inspected live signature, outputs and math rather than fabricating
an operator just to satisfy a template.

```text
tasks/<name>/
  meta.json               written by the agent (contract below)
  cases.py                written by the agent (contract below)
  unittest.py             GENERATED by generate_ut.py -- never hand-written or edited
  ut_runner.py            vendored unchanged by generate_ut.py (the one UT driver)
  harness_lib.py          vendored unchanged
  leg_runner.py           vendored unchanged
  overlay_setup.py        vendored unchanged
  kernel_src/             actual editable native/JIT/generated source
  baseline_overlay/       immutable baseline overlay configuration
  baseline_ref/           original hashes/source text, not imported as baseline
  captures/               optional minimal structural fixtures or fallback oracles
  run/                    declarations, raw traces, gate logs, results
```

Build the task with the generator from `$SHARED_TOOLS/`:

```bash
python3 "$SHARED_TOOLS/generate_ut.py" all "$TASK_DIR" --ranking "$RANKING_JSON"   # vendor + CPU check + freeze
cd "$TASK_DIR" && bash "$SHARED_TOOLS/../../kernel_workflow/scripts/gpu_lock.sh" "$GPU_ID" python3 unittest.py
```

`vendor` copies the four runtime files unchanged, writes `unittest.py` (its first
line is the generated marker the delivery gates key on) and registers the runtime
files in `meta.kernel_extraction.source_delivery_files` so the source snapshot binds
them. `check` reads `cases.py` without importing it and refuses missing hooks,
metadata, coverage buckets or a GPU-count mismatch (it names each problem in
`run/ut_check.json`; `--ranking` names the extraction's kernel ranking, see "Every
phase the kernel has calls in" below). `freeze` writes `run/ut_contract.json`: the hash of the test
contract (`unittest.py`, `cases.py`, `meta.json` with its tolerance, the runtime
files, `baseline_overlay/`, control files and the reference data you list in
`meta.ut_contract_files`). `kernel_src/` is not part of the contract: optimizing the
candidate source keeps the test valid, editing the test invalidates every earlier
result. Rerun `generate_ut.py all` after every change to `cases.py` or `meta.json`;
it reruns only the steps whose inputs changed, and every step after them. If a
helper needs its sibling capture/trace utilities, copy those too and list them in
`meta.kernel_extraction.source_delivery_files`.

## Metadata and adapters

`meta.target_callable` is an exact `module:attribute` spec. For a Python module
replacement, `candidate_bind` has `kind="module"`, `module` and a task-relative
`file` under `kernel_src/`. For rebind, use `kind="rebind"`, `target`,
`impl_module`, `impl_attr` and `file`. For a native/JIT leaf, the task-local Python
binding must build/import and invoke that local implementation; ship build
scripts/resources, version/arch flags and distinct module/cache identities.
Do not vendor an entire Python package merely to shadow one file.

The baseline is the installed serving stack plus immutable accepted overlays;
its callable must resolve outside the task. `_cand_overlay` adds the declared
candidate to that same baseline. `h.build_candidate_overlay(task, meta)` returns
`(baseline_overlay, candidate_overlay)`; then call
`h.assert_legs_differ(task, base, candidate, meta)`. A path difference alone is
insufficient: perform each claimed computation leaf's invocation and numerical
negative-control checks in separate untimed diagnostic processes.

`target_callable` -- in `meta.json`, `run/requested_kernel.json` and `run/RETURN.json`
alike -- is the entry the `kernel_selection.py` verdict certifies, e.g.
`SiluAndMul.forward`, not the class; `candidate_bind` may still bind the class. When
that entry resolves to the same code on both legs (a `forward` inherited from a base
class while the candidate overrides only `forward_native`), the candidate overrides
the certified entry itself so the legs differ there; never change `target_callable` to
pass `assert_legs_differ`. Only the full delivery preflight writes `run/RETURN.json`
([delivery contract](delivery-contract.md)).

`cases.py` exposes the functions the generated UT consumes (`h` is the vendored
`harness_lib`):

- `call(args)` invokes the declared entry under the ambient overlay and returns
  the complete output, including auxiliary tensors and in-place outputs (state a
  stateful kernel writes, e.g. the KV pages it filled, belongs in the output).
- `timing_cases(h, meta)` yields `{sig, regime, args}` and optional `m` for every
  declared timing case. Construct actual operands before the timed call. A case may
  set `inner` (default 1): the launches per timed sample. Under a graph deployment a
  small kernel whose one replay is shorter on the GPU than its dispatch reads
  host-bound (`primed=false`), and one replay of a kernel that runs a few us reads
  mostly the latency of launching the graph; the UT then raises that case's `inner`
  itself (see "Timing a graph-deployed phase" below). On one GPU (`world_size` 1)
  every sample of a graph-deployed case starts on a drained queue, so one replay also
  holds the latency of launching the graph -- about 15-35 us on a loaded host, moving
  with the host's load. For each such timing case with call mass, declare an `inner`
  that makes one replay's kernel time (`inner` x the per-launch time) at least about
  1 ms -- e.g. 512 for a 2-3 us launch, 32 for a 30-40 us one: the launch latency is
  then a few percent of the reading, and its swings move the reading by 1-2%. At
  0.1 ms it is 15-35% of the reading, which then follows the host's load (CI: the
  readings of a 2 us norm declared at 64 -- a 133-140 us window, 10-16% of it launch
  latency -- moved 3.4-8.3% between runs this way). Take the per-launch time from the
  profile or from a reading at a large `inner`: at `inner` 1 a few-us kernel reads
  mostly the launch latency, and multiplying that reading by `inner` overstates the
  window. With several GPUs (`world_size` > 1) the rank pools release every sample on
  the device and the launch latency stays out of the window; there declare an `inner`
  that makes one replay last at least 0.1 ms, as a shorter one can still read
  host-bound (`primed=false`). Either way the UT then needs no extra timings, and every
  run times the case with the same `inner`. A phase the server runs WITHOUT a CUDA graph
  is timed eagerly on a queued GPU spin (see "Timing an eager-deployed phase" below);
  there `inner` only amortizes event resolution.
- `random_shapes(h, meta)` yields `{sig, regime, make_inputs}`; the factory
  accepts a seeded torch Generator and varies values at the fixed served shapes.
  Preserve required routing semantics and the observed work/access pattern; reuse
  saved structural metadata rather than redrawing it blindly. A factory written
  `make_inputs(rng, ctx)` also receives the rank context (`ctx.rank`, `ctx.world`,
  `ctx.data_rank`, `ctx.rank_rng` seeded with the draw AND the rank); single-GPU
  factories may keep `make_inputs(rng)`.
- `eager_cases(h, meta)` yields `{sig, regime, args}` (at least two per phase, so
  output independence is checked). A `ref` is optional: the UT records the
  BASELINE's output of every comparison in a separate baseline process and judges
  the candidate against that, never against a reference the candidate computes.
  A `ref` you do supply (an independent math reference) is checked against the
  baseline.
- `replay(h, meta[, phase])` -- required for every phase deployed under a CUDA
  graph: the `run_correctness` replay bundle (`fill`, `run`, `read_out`, `cases`
  with >= 2 boundary shapes, `capture_idx`), or a list of such bundles. Each bundle
  is one replay group that records ONE graph and, in a generated task, names the
  deployment graphs it reproduces in `graphs` (see "Graph replay groups" below). In a
  generated UT a capture that fails is a FAIL, not a skip.
- `sequence_cases(h, meta)` -- required when `capabilities.stateful`: the ordered
  steps (with repeats) whose later calls read the state earlier calls wrote; they
  run through `check_correct_sequence` and are compared step by step. Every step
  names the stateful tier it exercises, `"tier": "<name>"` or `"tiers": [...]` (see
  "State carry and stateful tiers" below).
- `capture_context()` -- optional context manager entered around every graph
  capture (e.g. a framework's `graph_capture()`).
- Multi-rank only (`capabilities.multi_rank.world_size > 1`): `setup(h, meta, ctx)`,
  `teardown()` and `align(...)`; see [multi-rank UT](collective-ut.md).

For joint phases, include `meta.phase_target_callables` mapping each phase to
its live entry, and `meta.phase_regimes` mapping phase labels to observed
graph/compile settings. `cases.call` selects only those entries using frozen
phase metadata; a single candidate module may implement both. If multiple
modules/leaves are needed, use a tested local binding adapter and prove all
bindings. The stock harness's single `candidate_bind` is not automatic support
for arbitrary multi-module swapping.

`meta.json` adds, for a generated task:

```jsonc
{
  "device_kernel": "<the exact device kernel name of this kernel's ranking row>",
  "tolerance": {"tol": 0.02,                 // every output per_output does not name
                "per_output": {"2": 0.001}},  // optional: an output's own tolerance (step 0 (b))
  "capabilities": {
    "stateful": false,                      // true: sequence_cases and stateful_tiers required
    "multi_rank": {"world_size": 1},        // == run/requested_kernel.json required_gpu_count
    "per_output_compare": false,            // stays false: no comparison plugin (meta.compare)
    "single_rank_justification": ""         // only if kernel_src/ shows cross-device symbols
  },
  "phase_regimes": {                        // or one meta.regime; see "Graph replay groups"
    "decode": {"cuda_graph": true,
               "graph_capture": {"sizes": [1, 2, 4, 8], "pad": "up",
                                 "evidence": "server.log: cudagraph capture sizes [1, 2, 4, 8]"}}
  },
  "case_manifest": {
    "dims": ["regime", "m"],                // the coverage buckets ("档") of this task
    "cases": [{"sig": "decode_m4", "regime": "decode", "m": 4, "roles": ["timing", "correctness"]},
              {"sig": "decode_m8_max", "regime": "decode", "m": 8, "roles": ["correctness"],
               "boundary": true}]           // an end of the observed range ("Seeded inputs by default")
  },
  "random_draws": 3,
  "timeouts": {"setup_s": 900, "command_s": 3600, "total_s": 0},   // optional
  "controls": {"disabled": {}, "task": []},                       // see ut-validation.md
  "ut_contract_files": ["captures/structure.pt"],                  // reference data the test reads
  "timing": {"eager_spin_us": 600, "graph_inner_max_factor": 64}, // optional, see below
  "kernel_extraction": {
    "ranking_json": "<EVAL_DIR>/kernel_extraction/round_baseline/kernel_ranking.json", // generate_ut.py --ranking
    "source_origins": {"kernel_src/x.cu": "/abs/path/of/the/installed/x.cu"},   // copied source
    "binding_files": ["kernel_src/x_binding.py", "kernel_src/x_pybind.cu"]     // written for the task
  }
}
```

Every bucket of `case_manifest.dims` needs a timing case and a correctness case
(eager or random; a `"boundary": true` correctness case forms no bucket, see "Seeded
inputs by default"), and every positive-mass observed signature needs a timing case;
the generator names the missing bucket. The UT checks at run time that the cases
it actually ran are the declared ones. In a task with a graph-deployed phase the
dims also tell its deployment graphs apart; "Graph replay groups" below says which
dims that needs.

**Every phase the kernel has calls in.** Every phase in which this kernel has calls
in the extraction's kernel ranking (`kernel_ranking.json`: its row's `calls` or
`share_of_phase_pct` above 0) needs timing cases and correctness cases written with
that phase's deployed launch configuration. For example the decode rows of a mixed
prefill step run eagerly, pass the batch's actual `max_seq_len`, and reduce with
another `NPAR_LOOPS` instance than a decode step does. A TASK that names the kernel by
a phase ("the decode attention kernel") identifies the kernel; it does not limit the
phases. `served_regimes` does not set the scope of the UT either: every such phase is
a phase the kernel serves. `meta.workload.uncovered`
(`{"PREFILL": {"calls": n, "why": "..."}}`) only records the remaining calls of a
covered phase, never a whole phase; every entry has `calls` and `why`. A case or
`served_regimes` label belongs to a phase by, in this order:

1. `meta.phase_regimes.<label>.phase` (any case) -- write it when the name says
   otherwise, e.g. a `decode_mixed` label for the decode rows the ranking counts as
   PREFILL; `phase` may name several phases, as a list or joined with `+`
   (`"DECODE+PREFILL"`), and the label then belongs to each of them;
2. the label is the phase's name;
3. the label begins with `<phase>_`: `prefill_graph` and `prefill_eager` belong to
   prefill, `decode_lmhead` to decode.

`generate_ut.py check` reads the ranking named in `meta.kernel_extraction.ranking_json`
(`--ranking` writes it, see SKILL.md step 4; required when `meta.workload.kind` is
`agentx_trace_replay`) and finds this kernel's row by
`meta.kernel_extraction.ranking_row` (the row's id or name), else `meta.device_kernel`
(with every `joint_ut.phases[].device_kernel`), else
`meta.kernel_extraction.selected_device_kernels`, else the `device_kernel` of
`run/requested_kernel.json`; every name must find its row. It refuses a phase with
calls -- in the ranking, in `meta.workload.cases` or in `meta.workload.uncovered` --
without a timing case or a correctness case of a label belonging to it, or left out
of `served_regimes` when that is given. `coverage.calls.declared_uncovered` in
`run/ut_result.json` repeats `meta.workload.uncovered`.

`capabilities` must be honest: a kernel
declared single-GPU whose `kernel_src/` uses IPC handles, peer memory, symmetric
memory or collectives is refused unless `single_rank_justification` explains it
(e.g. a vLLM module copied whole that also contains an unused all-reduce).
Every source file in `kernel_src/` is one of two kinds, and the generator refuses an
unclassified one:

- copied source -- `source_origins` maps it to the installed file it was copied from;
- a binding file written for the task (a Python wrapper or custom-op registration, a
  pybind/extension file, build glue, a file that only instantiates or dispatches the
  copied templates) -- listed in `binding_files`.

Never list modified kernel code as a binding file. Verification measures the A/A
through the candidate's own binding: when every copied source is byte-identical to
its origin, the UT's own timing is that A/A measurement and is reused. A binding with
a different host path than the deployed wrapper is then visible, so keep the binding
thin.

Record `meta.workload` using the observed case model from `SKILL.md`. Keep
evidence paths and full signatures in the manifest. Shapes reconstructed from
median context or synthetic values are approximations, not captured joint
distribution coverage. Match cache residency to deployment; the vendored timer
has a cache policy, so inspect `h.cache_policy` and explicitly record its chosen
condition rather than treating defaults as measured deployment facts.

`meta.workload` is optional for the generator; AgentX extraction always records it
(`SKILL.md`). Without it the UT times the timing cases unweighted, as the legacy normal
mode does: the per-case lines are unchanged, the primary metric is the geometric mean
of the per-case speedups, printed as `GEOMEAN_SPEEDUP=<x>` with no
`GEAK_WEIGHTED_SPEEDUP` line, and every timing case counts as a case with call mass.
`run/ut_result.json` then has `timing.weighting.mode` `"unweighted"`, `timing.primary`
the geomean, `timing.weighted` null and per-phase geomeans in `timing.by_phase` (with
`calls` = the number of cases); the receipt says `"weighting": "unweighted"`.

### Graph replay groups

`replay(h, meta[, phase])` returns one group (a dict) or a list of groups. Each group
records ONE graph:

```python
{
  "fill": fill, "run": run, "read_out": read_out,      # as for run_correctness
  "cases": [...],                                      # >= 2 per group
  "capture_idx": 0,
  "graphs": [{"m": 8, "cr": 2}, {"m": 8, "cr": 1}],    # required in a graph phase: the deployment graph(s)
                                                       # this capture reproduces (case_manifest.dims here:
                                                       # ["regime", "cr"], so each graph has m and cr)
  "carry_state": True,                                 # optional (default False)
  "state": [ring_view],                                # required with carry_state: the persistent
                                                       # tensors (or a zero-arg callable returning them)
}
```

The generated UT records, replays and compares every group, strictly (a capture that
fails is a FAIL); the negative controls, the native reference recording and the
multi-rank agreed capture apply to each group. With >= 2 cases per group every replayed
graph sees at least two inputs. `graphs` has one entry per deployment graph the capture
reproduces: `m`, the captured size after padding, and every other `case_manifest`
dimension (all of `case_manifest.dims` except `regime` and `m`) with its value. Record
one graph per group, or one capture that issues the launch for several sizes, sites or
layers -- as a FULL decode graph holding every layer of the step does -- and list each
`{m, <dims>}` it issues. A group whose capture case
(`cases[capture_idx]`) is a timing case (same `sig`) must declare that case's deployment
graph.

Every graph-deployed phase declares how the deployment captures graphs, in
`meta.phase_regimes.<phase>.graph_capture` (without `phase_regimes`,
`meta.regime.graph_capture`): `sizes`, the M (batch / token) sizes the server captured;
`pad`, `"up"` when a step of M rows replays the graph of the smallest captured size
>= M (vLLM, SGLang) or `"exact"` when only exact sizes replay; `evidence`, where these
come from (e.g. the server log's capture sizes). Each timing case of a graph phase gives
its M as `m` in its `case_manifest` entry (or its `meta.workload.cases` entry). Before
any candidate verdict, the UT computes the deployment graph of every timing case with
call mass in each graph phase (every timing case without `meta.workload`): M padded to a
captured size, every other dimension as in the case,
`{"m": <M padded by pad>, <dim>: <the case's value> for each case_manifest dim besides
regime and m}` (`graph_capture.dims` may be left out; given, it must name exactly these);
a graph no group declares makes it exit 3 naming the missing graphs, and so does a case
whose M no captured size holds, e.g. above the largest one (it is not graph-replayed in
deployment: declare it in an eager phase). `generate_ut.py check` verifies the declaration format
and that every such timing case has an `m`. `coverage.graph.<phase>.deployment_graphs` in
`run/ut_result.json` lists exactly these graphs.

So choose `case_manifest.dims` with the deployment graphs in mind. In a task with a
graph-deployed phase, `dims` besides `regime` and `m` must include every dimension in
which this kernel's launches in that phase differ in static shape or configuration: the
call site or layer kind (e.g. the shared-expert d384 and the dense d2560 activation), a
width, a compression ratio. Timing cases with call mass that differ in such a dimension
are then different deployment graphs, and the coverage check above sees each of them;
left out of `dims`, they count as one graph, and a group replaying only one of them
passes. A bucket dimension kept only for coverage (e.g. a context-length bucket) is a
dimension of the deployment graph as well: a group whose replay covers several of its
values lists each `{m, <dims>}` in `graphs`. The generator does not check this for you:
two timing cases with the same M and `dims` may differ only in data, which is fine, or
in shape, which means a dimension is missing.

**Several launches per step, each launch's parameters choosing its path.** When the
deployment launches the kernel several times in one step and each launch's
parameters (e.g. `layer`/`nlayers`, `first`/`last`) decide the path it takes --
returning early or not, advancing an epoch or step counter or not, how a tag is
composed -- at least one group records, in one capture, >= 2 launches with the
deployment's per-launch parameters, covering every path a deployed step contains:
first, middle (when there is one) and last. That group declares `carry_state` and
replays >= 2 consecutive steps. The stateful tiers name the transition inside the step
(e.g. "a non-last-layer launch does not advance the epoch, the last one does"), and
`sequence_cases` covers it with steps of several launches. Every launch's output is
compared, directly or through the output of a later launch that reads it; say which.
Making every launch a step of its own (`layer=None`) does not replace this. The mono
kernel example is in [multi-rank UT](collective-ut.md), "A mono kernel launched
several times per step".

### State carry and stateful tiers

A task with `capabilities.stateful` and any graph-deployed phase needs at least one
replay group with `"carry_state": true` and >= 2 cases: consecutive replays carry the
state, as consecutive steps do in deployment. `fill` refreshes only the per-step
inputs: on every step after the first the UT checks that `fill` left the declared
`state` tensors unchanged (the first step may reset them, e.g. after the capture's
warm-up launches). The native references are recorded by the baseline running the
same steps in the same order, carrying the same state. Without such a group the UT
exits 3.

A stateful task also declares its stateful tiers, and every `sequence_cases` step
names its tier(s), `"tier": "<name>"` or `"tiers": ["a", "b"]`:

```jsonc
"capabilities": {
  "stateful": true,
  "stateful_tiers": [
    {"name": "prefill_tail_then_decode", "transition": "a chunk's last prefill rows, then decode steps of the same request"},
    {"name": "ring_wrap", "transition": "the per-request ring wraps mod 8 between steps"}
  ]
}
```

Take the tiers from the state transitions the deployment actually produces: a prefill
tail followed by decode, a ring / circular-cache wrap, an odd/even boundary, several
requests per step, ... A declared tier no step covers, a step without a tier, a step
naming an undeclared tier, or a stateful task without tiers makes the UT exit 3
(`generate_ut.py check` already names a missing declaration). Step counts are not
compared.

## Seeded inputs by default

Build `cases.py` from a fixed case manifest: shape, dtype, stride/layout,
quantization parameters, phase, seed and observed call weight. Use existing logs,
trace metadata and verified source/configuration to establish that manifest. If
needed, collect missing shape metadata once during extraction; UT execution must
never invoke `capture_shapes.py`, a profiler or the serving model.

Generate ordinary activations and weights directly with the supplied seeded
`torch.Generator`. Preserve each operand's valid range and format: scales may need
positive values, and packed quantized operands must be constructed with the real
packing/quantization contract. Use multiple fixed seeds and boundary-value cases;
random values alone do not cover ties, masks, empty rows or numerical extremes.
Boundary-value cases include both ends of the observed range: in every phase, and
for every call site `case_manifest.dims` tells apart, every size the kernel's work or
launch depends on -- tokens per step M, a chunk or query length, a context length --
needs a correctness case (eager; with random draws too when its inputs can be random)
at its smallest and at its largest value in the observed workload. Take the values
from the observed workload (its raw rows, or the ranges `meta.workload` records), e.g.
the scheduler's chunk budget (16384) and the shortest observed step. A size
that belongs to each request -- its context length or position, its chunk or
query length -- takes its ends over the requests: the shortest and the longest
single request in the steps this kernel runs in, from the per-request geometry
of the raw rows (`request_geometry` in `raw_decode_rows` / `raw_prefill_rows`
of `observed_workload.json`). A per-step figure is not such an end: the decode
buckets' `per_req_context_min` / `per_req_context_max` are a step's tokens
divided by its requests. Only when the log has no per-request geometry, use the
recorded range and say so in `meta.workload`. The M of a
graph-deployed phase needs both ends as eager correctness cases too; its replay still
follows the deployment graphs ("Graph replay groups"). Values outside the observed
range (e.g. `max_model_len`) are not part of this requirement. Declare such a case in
`case_manifest` with `"roles": ["correctness"], "boundary": true` and every dimension
filled in as usual: it needs no timing case and no `meta.workload` row and forms no
coverage bucket of its own, but the UT must still run and compare it (a declared
correctness case it never checked stops the UT with exit 3). A boundary case with the
timing role is refused. `coverage.boundary` in `run/ut_result.json` lists these cases.
Keep construction outside the timed region. Freeze the generator code and seeds
so baseline/candidate processes reconstruct identical inputs on the pinned stack.

The generated UT obtains reference outputs in isolated frozen-baseline processes
(`h.baseline_random_outputs` keyed by `sig|draw`, seed 0, `meta.random_draws`
draws, and a second baseline process recording every eager / graph-replay /
sequence output); input tensors need not be saved. Build eager cases from the same
seeded factories. Graph replay still needs its normal boundary cases and in-place
input refresh. A serving-captured `reference_io.pt` is optional; generated
reference outputs are not captures from the model.

For paged / cached state, write the cases so that wrong indexing cannot pass:
scatter KV block ids (shuffled, non-adjacent, e.g. `h.shuffled_block_table`) so an
implementation assuming contiguous blocks fails (ISSUE-022); include a far block
whose byte offset exceeds 2^31 (ISSUE-026); and for a kernel that writes a cache,
check the written contents AND that every byte outside the written range is
unchanged (ISSUE-040). These are authoring rules only; there is no generic control
for them.

Record which inputs are generated and which are structural fixtures. For MoE
routing, sparse indices, page tables and sequence state, first reuse existing
metadata or a validated reconstruction that preserves the observed work/access
pattern. Use a minimal structural capture only when those are insufficient.
Valid synthetic structures can test correctness, but random uniform routing can
change expert occupancy and gather locality, so report its timing scope honestly.

## Capture policy

Use `CAPTURE_PERSIST_POLICY=structure_only` when capture is necessary: retain
structural operands and reduce bulk float payloads to seeded descriptors. Integer
and boolean operands are structural by default; declare additional float structural
operands with `CAPTURE_STRUCTURAL_OPERANDS` / `meta.structural_operands`.

A captured output was computed from the original values, so it is not a reference
for regenerated random inputs. The reduced file is marked `oracle_status=needs_regen`:

```bash
python3 "$SKILL_ROOT/scripts/regen_reference.py" captures/reference_io.pt \
    --out captures/reference_io.regen.pt
python3 "$SKILL_ROOT/scripts/oracle_power.py" captures/reference_io.regen.pt --tol "$TOL"
```

This fallback persists reconstructed operands and baseline outputs. Prefer the
seeded factory above when it avoids capture entirely. Never regenerate structural
state through nondeterministic routing while pretending the inputs are unchanged.

## Correctness and timing

Use separate subprocesses for baseline and candidate. Import task helpers by
explicit file path and remove the task directory from `sys.path` before importing
torch: a file named `unittest.py` otherwise shadows Python's standard library.
The shared leg runner already performs this isolation.

0. **Before any verdict, prove the comparison can produce one.** Verify reproducible
   inputs, a tolerance supported by baseline self-noise, and effective numerical
   negative controls. For a seeded task, run these checks on generated cases and
   frozen-baseline outputs without collecting a serving oracle. The following
   helper commands apply when their input formats match: `oracle_power.py` for a
   saved capture and `kernel_self_noise.py` for a shape-by-M `_build_args` adapter.

   ```bash
   # (a) can the captured oracle reject anything?
   python3 "$SKILL_ROOT/scripts/oracle_power.py" captures/reference_io.pt --tol "$TOL"
   # (b) does the installed kernel reproduce itself, and are the inputs even stable?
   python3 "$SKILL_ROOT/scripts/kernel_self_noise.py" --repeats 5 [--packed] \
       --out "$TASK_DIR/run/self_noise.json"
   ```

   (a) A phase that runs entirely inside a CUDA graph fires python-level capture
   hooks only during graph **capture**, when the buffers are placeholders. On a
   real decode seam this recorded every float operand and the output as identically
   zero while the integer index operand looked real — so "is the file all zero"
   would have passed it, the control computed `0 * 0.5 == 0`, and the report said
   `max_rel_err: 0.0`, which reads like a perfect pass rather than an empty one.
   Capture during graph **replay** in steady state, or take a bounded eager
   diagnostic leg and revalidate the timing in deployment graph mode.

   If the capture turns out to carry no usable values, a reference generated by running
   the installed, unmodified kernel is a legitimate substitute — say so in
   `meta.oracle_coverage`, since gate 1 against it is then a determinism check rather
   than a deployment-value check. **Persist the exact operands it was computed from
   alongside the output.** Rebuilding them at UT time reintroduces (b) inside the
   correctness gate, where it is much harder to see than in a probe.

   (b) A tolerance below the installed kernel's own noise floor decides nothing.
   Establish the floor with ONE set of args reused across repeats, and only after
   phase 1 shows the args are reproducible: on this deployment
   `aiter.fused_moe.moe_sorting` returns different routing metadata from
   bit-identical inputs, so rebuilding args inside the repeat loop reports the
   routing change as kernel nondeterminism. For packed sub-byte payloads
   (MXFP4 values + exponent bytes) the only meaningful criterion is byte-exactness;
   `rel_frobenius` over packed bytes is not a number about the computation.

   When the reference output cannot be reproduced bit for bit (split-K atomics, a
   nondeterministic reduction), size the tolerance from the UT's own self-noise.
   Measure `noise_rel` at least 3 times, e.g. run `python3 unittest.py --correctness-only`
   3 times and read `native_noise.noise_rel` from its result
   (`run/ut_partial/correctness-only/ut_result.json`; it is recorded even when the
   tolerance is too tight and the run stops with exit 3), and take the largest, N.
   `noise_rel` is the native refs leg against the native oracle on the random draws on
   `correct()`'s own scale: `correct()` passes at a tolerance t exactly when
   noise_rel ≤ t. Set tol to the smallest of {1, 1.5, 2, 3, 5} × 10^k that is at least
   2N (one step more when the runs differ a lot) and write each N and this choice into
   `meta.tolerance`. Do not size it from `max_rel_err`: its denominator holds tol itself
   (|ref| + tol·RMS), so on references near 0 it reads the share of the tolerance band
   used, and sizing from it inflates the tolerance with the square root of the noise.
   For the same reason a passing row may read `max_rel_err` above tol (up to 1):
   `verify_ut.py` holds the self-noise to noise_rel ≤ tol/2 and only failing rows above
   tol, so it accepts the tolerance sized here -- do not raise it for such rows.
   For example a split-K MoE output of RMS 0.383 whose zero reference elements move by
   0.0039 between runs has noise_rel 0.0102: tol 0.03, where `max_rel_err` would ask for
   0.15 or more. A kernel that reproduces bit for bit (N = 0) keeps a tolerance set from
   the semantics, as before.

   `correct()` holds every output of a comparison to one tolerance. When the outputs
   differ in numeric type or scale -- e.g. a bf16 hidden state, an f32 mixing weight and
   an fp8 cache record compared decoded -- size each output's tolerance from its own type
   and its own self-noise and write it into `meta.tolerance.per_output`
   (`{"<output>": <tolerance>}`); `tol` covers the outputs it does not name. A single
   `tol` for every output must not be looser than any output needs: an f32 output held
   to a bf16 tolerance lets errors through that the right tolerance rejects. Name an
   output by its position in `flatten_outputs` order (`"0"`, `"1"`, ...; a tuple in order,
   a dict by sorted key) or, when what the task compares is a dict, by its key (every
   tensor under it); one task names its outputs one way, and every comparison of the
   task must compare the same outputs. The UT then compares output by output, each at
   its own tolerance, on both legs and every rank; `within_tol` and `scale_out` move each
   output by its own tolerance; `native_noise.per_output` records each output's
   `noise_rel`, the self-noise rule holds each output to half its own tolerance, and
   each tolerance is sized from its output's N as above. `generate_ut.py check` checks
   the format; an output the compared output does not have (a position past the last
   one, a key the compared dict lacks, a key for an output that is not a dict, a position
   for a dict), or two comparisons that compare different outputs, stop the UT with
   exit 3. A comparison plugin (`meta.compare`, `capabilities.per_output_compare`) is
   not supported and is refused.

### Timing an eager-deployed phase

A phase deployed under a CUDA graph is timed as a graph replay. A phase the server
runs without one (`phase_regimes.<phase>.cuda_graph` false, or `enforce_eager`) is
timed eagerly. Every sample starts on a drained queue (cache flush, then sync), so a
plain eager window opens with the GPU idle, waiting for the host to issue the first
launch. For a small op that dispatches slower than it computes, that reading is the
host's dispatch latency -- and the two legs' bindings dispatch differently, so the
same kernel reads as a speedup or a slowdown. The generated UT therefore queues a GPU
spin on the stream after the flush and sync and before the start event:

```text
flush -> sync -> GPU spin -> [spun event] -> start -> inner calls -> end -> query(spun event)
```

While the GPU spins, the host issues the start event, the `inner` calls and the end
event; the window then holds the GPU running them back to back, which is the GPU
execution time. The spin lasts max(200 us, 2 x inner x the measured dispatch of one
call); `meta.timing` may set `eager_spin_us` (a fixed spin), `eager_spin_min_us`,
`eager_spin_factor` or `eager_spin_late_limit` (positive numbers). A sample is late
when the spin had already ended once the end event was queued; more than 5% late
samples doubles the spin and measures the case once more, and if that is late too the
receipt says the case's reading includes dispatch. Graph timing, multi-GPU timing
and hand-written tasks are unchanged.

### Timing a graph-deployed phase

A phase deployed under a CUDA graph is timed as replays of a graph holding `inner`
launches; every reading stays per call (divided by `inner`). One replay of a small
kernel can be shorter on the GPU than issuing it takes, so the reading is
host-dominated (`primed` false). For every timing case with call mass in such a phase
(every timing case without `meta.workload`), when either leg reads `primed` false the
UT doubles the case's `inner` and times both legs again with the same `inner`, until
both legs are primed, and keeps the smallest such `inner`. The cap is
`meta.timing.graph_inner_max_factor` (default 64) times the declared `inner`; only a
case still host-dominated at the cap stops the UT with exit 3, naming the case, its
`host_ms` and `ms`. The receipt records each raised case's
`"inner": {"declared": 1, "final": 8, "tried": [1, 2, 4, 8], "reason": "..."}`. The
multi-rank timing and the kernel lane's runs of the same `unittest.py` do the same;
eager-deployed phases (above) are not affected.

`primed` compares the host's cost of issuing a replay with the reading, so it does not
see the other fixed cost of a window: every sample starts on a drained queue, and one
replay's window also holds the latency of launching the graph, about 15-25 us on a
loaded host. A kernel of a few us then reads that latency and its jitter, on every M
(an A/A of a 3 us norm moved 10% this way). The UT therefore also times every such case
whose replay window (`inner` x the per-call reading) is under 0.1 ms on either leg
once more on both legs, at 16 x its `inner` (at most the cap), timing every pair (no
early stop: one outlying fresh process must not set the `inner`). A reading at `inner` n
is K + E/n (E the per-replay floor, K the per-launch time in a packed graph, as in the
deployment's graph), so the two readings give E and K for each leg. When E/n is over
10% of either leg's reading, the case is raised: if the probe's reading already holds
at most 10% of floor on both legs, the case takes the probe's `inner` and reading;
otherwise its `inner` is raised to the smallest value at which E/`inner` is predicted
to be at most 10% of both legs' readings (9 E/K rounded up, at most the cap), timed
once more on both legs (every pair), and that reading is kept. A case whose floor is
at most 10% keeps its `inner` and reading, and the receipt records the check as
`"inner_floor"` (with `probe_failed` when the probe returned no reading). A raised
case's `inner` record carries `floor` (`probe_inner`, `floor_us`, `kernel_us`, the
floor's share of each leg's reading at each `inner`). A case whose floor is still
over half of a reading at the cap stops the UT with exit 3, naming the case, its floor
and `ms`. The UT probes only windows under 0.1 ms. A case declared with a longer
window is not checked: on one GPU a window between 0.1 ms and about 1 ms still holds
3-35% of launch latency, and its reading follows the host's load -- declare the
`inner` described under `timing_cases` above. A raised case that takes the probe
keeps the same `inner` from run to run. One that needs more takes 9 E/K from that
run's E and K: in CI its `inner` moved by 5-21 launches between runs and its reading
by 1.5-3.5%, mostly the kernel's own time differing between fresh processes (the
floor stays near a tenth of the reading). A case raised to the cap (a 2 us launch
raised from 1 to 64) still holds 10-20% of floor, and its reading follows the host's
load. A case whose window is close to 0.1 ms can still be probed in one run and not
in another, its reading then moving by about the floor's share (15-20%). When a full
run raised a case, write into `cases.py` before freeze the larger of the receipt's
final `inner` and the `inner` asked for under `timing_cases` (on one GPU, about 1 ms
of kernel time): every later run (verify_ut, the mutation runs, the lane's three full
runs) then times it without the floor timings, each of which costs one timing of both
legs (about 40-80 s on one GPU).

The shared tensor checker assumes independent returned outputs. If the actual
serving contract permits persistent/in-place buffers, document that contract
and return independent snapshots from `call`. Do not silently present an
incompatible generic tensor gate as passing.

## What the generated UT does and prints

`python3 unittest.py` (= `ut_runner.py`) runs, in order: the contract check, the
source snapshot, the binding check (both legs resolve to different code, the
baseline outside the task), the baseline oracle, the baseline reference process,
the candidate correctness process (which also reports the identity it actually
resolved), the timing legs and the weighting. Options: `--correctness-only`,
`--timing-only`, `--mutation <leaf>` (a source-mutation run, correctness only). Only
a full run writes `run/ut_result.json`: a partial run without `--out` writes
`run/ut_partial/<mode>/ut_result.json`, a mutation run
`run/mutations/<leaf>/ut_result.json`. A partial result carries `full_result`
`{"path": "run/ut_result.json", "current": true|false, "why": ...}` -- whether the last
full UT (exit 0) has this run's `contract_sha256` and `snapshot_sha256` -- and the run
prints `[ut] full UT result run/ut_result.json: current ...` or `... stale (...)`. Every
run prints:

```text
[ut] contract <contract_sha256>
[ut] snapshot <snapshot_sha256>
CORRECTNESS: PASS|FAIL
case <sig>: baseline_ms=.. optimized_ms=.. speedup=.. reps=.. timer=.. primed=b/c host_ms=b/c
GEAK_WEIGHTED_SPEEDUP=<x>          (without meta.workload: GEOMEAN_SPEEDUP=<x> instead)
GEAK_TIMING_RECEIPT: {"all_primed", "timer_unprimed", "cache_mode", "world_size", "timer", "alignment", "flags": [...], "cases": {...}}
UT_RESULT: {"ok": .., "exit_code": .., "result": "run/ut_result.json"}
```

`run/ut_result.json` carries `ok`, `smoke`, `exit_code`, `target_callable`,
`snapshot_sha256`, `contract_sha256`, `world_size`, `gates`, the correctness
reports (every graph-replay row names its `group`; each phase lists its
`replay_groups` {group, graphs, carry_state, steps, capture_sig, ok}), the native
run-to-run noise (`native_noise`: `max_rel_err`, `cases`, `noise_rel`, and with per-output
tolerances `per_output` {output: {tol, noise_rel}}; recorded also when the baseline fails
the task's own checks), with per-output tolerances also `tolerance` {tol, per_output,
outputs: [{output, tol}]} and in every correctness row the `output` whose error the row
records and that output's `tol`, `timing.per_case` (with both legs' timer, `primed`, `host_ms`, cache
condition and every rep's ms), `timing.weighting.mode` (`observed`, `analytic` or
`unweighted`), `timing.primary` (the weighted speedup, or the unweighted geomean),
`timing.by_phase`, `receipt` and `coverage` (below). A case whose `inner` the UT
raised has an `inner` record in the receipt (see "Timing a graph-deployed phase").
In the receipt each case says whether its phase is `deployed_graph`; an
eager-deployed leg adds `spin` {queued, us, samples, late, retried,
includes_dispatch} and `latency_ms`, the device reading of a few extra samples
without the spin: the dispatch-inclusive latency, a reference that is never scored
(`wall_ms` keeps its meaning, host plus device of such a sample). `flags` lists, without
failing the UT, every eager-deployed leg whose dispatch is slower than its GPU time
(`primed` false: it is scored on GPU time, which presumes the host runs ahead of the
GPU in deployment) and every leg whose spin ran out even when doubled. Exit codes:
0 pass; 1 the candidate fails correctness or cannot be timed like the baseline;
2 environment (GPU memory, lock, IPC fault, time limit); 3 the UT itself is
incomplete (contract changed, missing replay/sequence hooks, the baseline fails the
task's own checks, an uncovered bucket, a deployment graph no replay group declares or
a graph-phase case no captured size holds, a stateful graph task without a
`carry_state` group, a missing, undeclared or uncovered stateful tier, a graph case
still host-dominated, or still mostly the graph launch floor, at the `inner` cap, an
eager-deployed single-GPU case timed without the spin).

`coverage` records what the run covered, single- and multi-rank alike (the group and
tier data come from the native reference run, on every rank):

```jsonc
"coverage": {
  "weighting": "observed",                   // or "analytic", "unweighted"
  "buckets": [{"bucket": {"regime": "decode", "m": 4}, "timing": ["decode_m4"], "correctness": ["decode_m4"]}],
  "boundary": [{"sig": "decode_m8_max", "regime": "decode", "dims": {"regime": "decode", "m": 8}, "checked": true}],
  "calls": {"with_calls": [...], "timed": [...], "uncovered": [...],         // signatures
            "declared_uncovered": {"PREFILL": {"calls": 960, "why": "..."}}},   // meta.workload.uncovered
  "graph": {"decode": {"capture": {"sizes": [1, 2, 4, 8], "pad": "up"}, "dims": [],
                       "deployment_graphs": [{"m": 4}, {"m": 8}],
                       "groups": [{"group": 0, "graphs": [{"m": 4}], "carry_state": false, "steps": 2, "ok": true},
                                  {"group": 1, "graphs": [{"m": 8}], "carry_state": true, "steps": 3, "ok": true}],
                       "missing": []}},
  "state": {"stateful": true, "carry_groups": [{"phase": "decode", "group": 1, "steps": 3}],
            "tiers": {"declared": ["ring_wrap"], "covered": {"ring_wrap": ["<step sig>", ...]}, "uncovered": []},
            "sequence_steps": 84}

```

A generated UT is stricter than a hand-written one: a graph capture that fails is a
FAIL, both legs must use the same timer, and every positive-mass case of a graph
deployment must be device-dominated on both legs, and not mostly the graph launch
floor (the UT raises `inner` until it is, up to the cap), and replayed in its
deployment graph.

Freeze the source/test snapshot before GPU gates. Generate leaf/source evidence as
described in [source records](source-delivery-records.md), then verify the test
with `verify_ut.py` as described in [UT validation](ut-validation.md). Keep all raw
logs; JSON declarations alone do not establish execution truth.
