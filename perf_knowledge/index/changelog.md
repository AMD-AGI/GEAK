## aiter PR-review skill ingested as a workflow + four amendments (2026-09-21)
- **Tiered merge, not a copy.** `ROCm/aiter@04c7b808:.claude/skills/review-pr/{SKILL.md,rules.md}` (504 + 618 lines) is an *executable agent procedure* bound to one repo: `fetch.sh`, `triage.py`, a `$WORK` artifact directory, six machine gates, a file-tier table naming aiter paths, and a CI label roster. None of that runs in GEAK and none of it was ingested. What came across is the part that holds for any AMD kernel PR, split across one new workflow and four amendments to existing cards.
- **New**: `workflows/review_kernels.md` (`kind: workflow`) — the first review-shaped document in the base. It answers a different question from every other workflow: the others ask "how do I make X faster and bank it", this asks "should I believe this change is correct and faster", so the gate is on evidence quality rather than on a delta. Carries the **advisory vs deterministic** split (the central discipline — a reviewer judgement never gates, only a reproducible blocker that ships its own reproducer may), the blast-radius tiering, the defect catalogue reorganized **by mechanism** rather than by upstream's rule ids (coverage gaps / silent bypass / hardcoded arch-dtype / uninitialized state / cross-repo / Triton-Gluon / hardware limits), the six AI-code structural checks, the refutation ladder, and the finding format (Problem → Impact → **Action ending in a verb**, tagged `[verified]`/`[inferred]`).
- **The false-positive guards are carried with every rule, deliberately.** Upstream's rules each ship a "before you fire this" check, and they exist because the unguarded version produced noise: an unmasked `tl.load` on a provably-aligned dim is safe, `max_size=True` on a full-size weight is correct, a hardcoded `fp8_max` on a single-dtype path is fine, an arch string already present elsewhere in the file is pre-existing style, and excluding a one-time weight preshuffle from steady-state latency is correct methodology rather than deception. A catalogue without them is a noise generator; that is the failure mode the card names in its pitfalls.
- **Two measured cautions kept verbatim because they are the load-bearing part.** (1) *Do not reduce a structural rule to a name list* — upstream's int32-overflow rule listed `token_id`/`seq_start`/`batch_offset`, missed three real defects using other names, and the name-matching scanner reported **0 of 4** real lines on one PR while emitting 390 candidates. (2) *Self-refutation is the weaker tier* — four rounds of tooling work moved self-refutation pushbacks from 64 to 33 and moved an independent reader's **28%** kill rate not at all. The 28% is recorded as an **upper bound** (the adversary was never itself audited), and the number that would actually matter — the rate of false *clearance* — has never been measured, which is why the whole tier stays advisory.
- **Amendment 1 — `profiling/benchmarking_methodology.md`** gains a "reviewing someone else's number" section: base vs head on one box, back to back, from clean trees at the exact compared revisions, because running only head against the author's chosen baseline reproduces their comparison, cannot show a regression, and inherits their baseline's staleness. Adds an explicit ratio convention (`candidate/base` for higher-is-better, `base/candidate` for lower-is-better, so `<1` always means regression), requires matched rows and clean exits, and separates five "could not measure" states. It also resolves timing-window exclusions in both directions: one-time amortizable cost (weight shuffle, model load, cached JIT) should be excluded; a cost recurring per call or cold start may not; charging a one-time shuffle against a single call to manufacture a regression is the same error inverted.
- **Amendment 2 — `quantization/fnuz_vs_ocp.md` had a line that actively misleads on kernel code.** The card said "gfx942 vs gfx950 is the line", true for *checkpoints* and wrong for *dispatch logic*: **one arch can have both fn and fnuz tensors in flight** (on gfx942 the KV cache is fnuz by default while a Q-quant path may emit OCP fn). That line is now scoped to checkpoints and a new section states the narrow rule — gating a *conversion* by arch is correct, *inspecting* what a tensor already is must compare `tensor.dtype`, and `fp8_max = 240.0` must be derived from the dtype since it is silently wrong for OCP e4m3 (448).
- **Amendment 3 — `optimization/lds_and_bank_conflicts.md`: capacity is not the same as an instruction's immediate window.** gfx1250 exposes **320 KB addressable LDS**, while an ordinary `ds_read`/`ds_write` immediate offset covers 65535 bytes. The effective address also has a VGPR base, so this is **not** a 64 KB allocation ceiling and crossing it does not guarantee a spill or compile failure. The review check is narrower: large layouts can require extra address arithmetic and VGPR liveness, so inspect generated DS addressing and the resource report before claiming a regression. The 320 KB figure previously existed only in `hw_constants.json` inside the Gluon skill, and `hardware/` had no gfx1250 coverage.
- **Amendment 4 — three safety corrections to `languages/flydsl/authoring_api_migration.md`**, ingested six days earlier and directly contradicted in two places by the review rules. (a) §2 recommended `make_buffer_tensor(tensor, max_size=True)` as the mirror of `create_buffer_resource` with no warning; on a **runtime-ragged** bound dimension that declares the buffer as large as its allocation and the hardware `num_records` permits reads past live data — silent garbage, no fault (aiter#4151 → #4546). (b) The pinned `b0ced008` helper documents `flyc.compile` as compile-and-execute, while the later review rules say it only compiles and report a cache-miss no-op (aiter#3987). The contracts are version-dependent and cannot be papered over by always calling the returned function, which would double-launch on the former; the card now requires using the helper shipped with the runtime and testing first-call behavior before writing a custom shim. (c) §1 tells you to replace `arith.unwrap`, but `arith.bitcast` still **requires** an unwrapped operand or it is a JIT-time type error surfacing only when that dtype branch first compiles (aiter#3944).
- **`taxonomy.md` gains `gfx1250` (CDNA5, MI450)** as a controlled gen id. Three docs were already using it in frontmatter against a vocabulary that listed only gfx906/908/90a/942/950, so this ratifies existing usage rather than introducing it; `lds_and_bank_conflicts.md` now carries it too.

## aiter op-test standard ingested as amendments only (2026-09-21)
- **No new doc, deliberately.** `ROCm/aiter@04c7b808:.claude/skills/aiter-op-test/SKILL.md` prescribes the structure of an aiter `op_tests/test_*.py`. Roughly two-thirds of it is either aiter-API machinery (`@benchmark`, `run_perftest`, `checkAllclose`, `aiter.logger`, the argparse conventions, `itertools.product` sweep shape, the markdown-table deliverable) or ground GEAK **already covers more deeply**: TFLOP/s-vs-GB/s dual reporting with the memory-bound reading rule is in `expert_skills/tuning/benchmark/README.md`; fp32 references, per-dtype tolerances, `err_ratio < 0.05` and the FP8-dialect check are in `expert_skills/tuning/tuning-core/correctness_gates.md` with measured K-sweep tables the skill has no equivalent of; capture-shapes-live and the immutable oracle are in `workflows/optimize_single_kernel.md`. Writing a new card would have duplicated all of that at lower quality. Four things were genuinely absent and were placed where they belong.
- **Amendment 1 — `workflows/optimize_single_kernel.md` Step 1: right shape is not enough.** The step already insisted on live-captured shapes, but shape does not capture **buffer ownership** (the model passing a preallocated `out=`/`YQ=`), **real tensor layout** (a transposed *view*, not a fresh contiguous tensor of the same shape), or the **coupling between input and output layout**. A test using idealized contiguous inputs where the model uses a view reports the wrong perf *and* hides the strided-input bugs. Also adds the derive-don't-guess fallback for when capture is impossible: read the model's real `config.json` rather than dataclass defaults, write the semantics→`(b,m,n,k)` mapping down, and note that **the parallelism config changes the batch dim** — with grouped output projections `b = groups / tp`, so an `o_groups=8` op is `b=1` at tp8 and `b=4` at tp2, and an `o_groups=16` one is `b=2` at tp8 and `b=16` under dp. One shape row is not one coverage point.
- **Amendment 2 — `profiling/benchmarking_methodology.md` gains candidate-table hygiene** for multi-backend bake-offs: the torch reference is computed and compared but never timed into the table (unless torch is itself a kernel under test); a candidate that is wrong in a config must be dropped *with the reason stated* rather than left to post a wrong-but-fast number that wins the bake-off; the error column is how those are found, so a candidate near `err ≈ 0.99` is never silently removed before deciding whether it is an unsupported config or a real bug; and the arch goes in the row so a table stays self-describing when two cards' results sit side by side.
- **Amendment 3 — `operators/layout_shuffle/overview.md` gains an arch-scope section.** Pre-shuffle matches a specific MFMA fragment layout and is therefore **arch-conditional, not a universal win**: on **gfx1250 (CDNA5) the FP8 path is a linear layout and the shuffle must be off** (`preshuffle=False`) rather than inherited from a gfx942/gfx950 recipe. Adds the paired-test caveat — gate the reference with the kernel, or the test fails for the wrong reason. Card now carries `gfx1250`.
- **Amendment 4 — `workflows/review_kernels.md`** structural check 5 (tests calibrated to pass) gains two tells that pass review easily: a test feeding idealized contiguous inputs where the model feeds a view or a preallocated buffer, and an arch gate written as a **deny-list**, which silently runs an unbuilt kernel on the next new card where an allow-list skips cleanly.
- **Not ingested**: the `test_quant.py` template, the `@benchmark`/`run_perftest`/`checkAllclose` API contract, aiter's argparse flags, the one-table-per-signature rule, and the anti-pattern list — all bound to aiter's test harness.
- **No operator or card-count change**: 54 operators, 226 cards, registries untouched.
