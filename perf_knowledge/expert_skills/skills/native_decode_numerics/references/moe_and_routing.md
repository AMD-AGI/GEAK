# MoE experts and routing: native numerics facts

Operators: MoE routing / top-k (`moe_routing_topk`: gate GEMM, logits rounding, scoring, selection bias, groups,
tie and id-order rules, renormalisation, routed scale, weight dtype) and MoE experts (`fused_moe_grouped_gemm`,
`grouped_gemm_moe`: activation quantisation, weight and scale layouts, the expert GEMMs and their rounding
points, activation, where the routing weight is applied, the top-k combine). Backends: vLLM on ROCm, with
aiter's HIP / CK / Triton kernels or vLLM's own C++ and Triton kernels. Not here: SGLang (`sglang_backends.md`),
the dense linears around the MoE (`linear_and_gemv.md`), the TP all-reduce after it (`tp_allreduce.md`), and how
to compare (`parity_method.md`).

**Versions.** Line numbers are valid at vLLM commit `f09d5e30c`, aiter tag `v0.1.26` (rows marked
`@285579b6` were read at that aiter commit) and, for SGLang, commit `22e1cb6d98`; in any other version
locate the code by symbol.

**Status.** `capture` = verified on a model capture (a captured decode step of a served model was reproduced
with this fact; "2 models" when two served models agree). `probe` = verified by a real-op probe (the installed
native op was run on synthetic inputs and compared with an emulation of this fact, usually bit for bit).
`source only` = read from source, never run against the native op: treat it as a suspect and confirm it with
the flip test in `parity_method.md` before relying on it.

**Model-package tags.** Some rows cite per-model packages under `vllm/models/`; resolve a tag by listing
`vllm/models/` in the checkout.
- `<PKG_LATENT_SPARSE>` = the package of the sparse-latent-attention generation these rows were read in: of the
  two packages that contain `sparse_mla.py` and `compressor.py`, the one that also contains
  `common/ops/fused_indexer_q.py`. For `DeepSeek-V4.1`, check that the same symbol exists in its own package
  before relying on a row; until then the row is `source only` for it.
- `<PKG_POSTNORM_MOE>` = the package of the post-norm MoE model with fused norm / routing kernels (contains
  `common/ops/fused_rmsnorm.py`).
- `<PKG_SMLA_PREV>` = the package of the previous sparse-MLA generation (contains `common/kernels.py`).

**Effect sizes (routing).** A routing comparison checks the expert ids exactly, position by position, and the
weights against a bound derived from the fp32 arithmetic. "N × tolerance" is how far the wrong variant lands
outside that bound on synthetic shapes; "invisible" means below it, so only an exact-tie test or a bit-level
probe can show the difference. One swapped expert is a failed comparison, whatever the weights do.

`DeepSeek-V4.1` belongs to the same family as the sparse-latent-attention MoE model whose sqrt-softplus router
rows are listed here and has its own package: re-confirm those rows there.

| id | Fact | Applies to | Status | Effect if wrong | Source |
|---|---|---|---|---|---|
| MOE-23 | aiter HIP `opt_sort` kernel: a group's score is the sum of its two largest biased scores; the groups whose score is at least the 4th-largest group score are kept, strictly larger first, ties to the lower group id. | vLLM · `GroupedTopKRouter` + aiter HIP top-k (256 / 8 / 4 / top-8) · gfx942 | source only | top-2 sum against max keeps different groups on a large share of rows (no multiple given) | aiter: `csrc/kernels/topk_softmax_kernels_group.cu:1167-1234`, `:1272-1286` |

## Near ties

The ids are compared exactly, so a routing comparison is only meaningful where the selection does not hinge on
one fp32 rounding. The general method is in `parity_method.md`; the routing-specific points:

- **Exact ties are decidable: test them.** Duplicated gate rows (with their bias) and, with bf16 logits, equal
  rounded logits give bit-equal scores, which the tie rule of the kernel decides on both sides (table above).
  Build such rows on purpose; they are the only inputs that tell a lower-id kernel from a higher-id one.
- **Near ties are not decidable: skip them and count them.** Against a captured step the native logits and the
  candidate's differ by fp32 noise, so a token whose k-th and (k+1)-th biased scores are closer than that noise
  may swap one expert. Accept either routing for tokens whose k-th / (k+1)-th biased scores are within a relative
  threshold and report how many tokens were skipped. A grouped router adds the kept-group boundary as a second
  near-tie source: compute the margin on the group scores too.
- **How common** (`capture`, 1 model): on `MiMo-V2.6-Flash` (sigmoid scores plus bias, one group, top 8 of 256,
  bf16 gate weight, fp32 logits) 5 of 14 captured steps of one MoE layer contained a token whose 8th and 9th
  biased scores differed by less than 1e-3 relative, while one bf16 ulp on the router input moves that gap by up
  to about 4e-3 relative. The thresholds that made the comparison stable ranged from about 8e-4 to 8e-3
  relative, depending on the layer.
- **sqrtsoftplus.** A logit error of d (absolute) moves a score by at most d / 2 relative, but `log(1 + e^l)`
  loses relative accuracy for picked logits far below zero, which table layers can produce (any expert can be
  picked): compare those weights with an absolute floor, not a purely relative bound.

## Not covered by any check

Routing:
- The grouped biased-sigmoid kernel was read only for 256 experts / 8 groups / keep 4 / top-8 with aiter's fused
  MoE on. Other configurations take other aiter kernels (register / LDS variants) or, with aiter off, a torch
  grouped top-k built on `torch.topk(sorted=False)` with no defined id order: not read for vLLM (the register
  variant that SGLang reaches is described in `sglang_backends.md`).
- The tied order of the aiter HIP `opt_sort` kernel (MOE-24) and its group rule (MOE-23) were never run against
  the native op; no test shape has duplicated experts for it.
- aiter Triton routing (monolithic mxfp4 experts): only the sigmoid score mode with one group, a bias and fp32
  logits was seen on captures. The higher-id tie rule, bf16 logits, the flat softmax path, the grouped Triton
  top-k and the `AITER_TRITON_USE_HERD` variant were not exercised. Its sqrtsoftplus score mode was not read as
  facts; it evaluates softplus as `max(x, 0) + log(1 + exp(-abs(x)))`, another fp32 form than the C++ op of MOE-17.
- Softmax routing with real groups or with a correction bias; where the routed scaling factor is applied for
  the plain softmax router when it is not 1.0; aiter's legacy softmax launcher (above 4096 tokens or off
  gfx942 / gfx950): not read.
- Fused shared-expert slots appended to the routed top-k buffer (`VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS`):
  the router output then has more than k columns; not covered by the routing rows.
- `topk_softplus_sqrt` was read for gfx942 with a bf16 gate weight and aiter's fused MoE on. Not read or not
  modelled: the gfx950 gate GEMM tiers, an fp32 gate weight, fp16 logits, layers that route image tokens with a
  second bias, and the other top-k helper a score layer may take with aiter's fused MoE off. The op exists for a
  fixed list of expert counts (powers of two up to 512, plus 192, 320, 384, 448 and 576).
- The `topk_softplus_sqrt` probes ran an installed build of a slightly different vLLM revision than the one whose
  source lines are cited; they show that the built kernel behaves as the cited source on the probed cases.
- Router of the post-norm MoE model: every row is `source only`. One real-op run of the whole fused routing path
  exists (ids equal, weights within about 2e-7 relative, sigmoid and softmax, with and without multiplier and
  eps), but it does not test the rows one by one: it cannot, for instance, separate `sum + eps` from
  `max(sum, eps)` at eps 1e-15. Its CPU path (`torch.topk`) and the gfx950 three-plane GEMM were not run.

- The CK epilogues behind `MOE-72` and `MOE-84` were read, not run; no capture or probe separates the rounding points of
