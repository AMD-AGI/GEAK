# AMD CDNA4 — SKU planning peaks (gfx950)

**Planning models, not sustained rates.** Microarchitecture: `planning-constants.md` §gfx950.
Lever gate: `capability-matrix.md` (`mfma_scaled` on gfx950 only).

```text
saturation = grid_tiles / CUs
L2_MB      = per-GPU L2 (8 XCD × 4 MiB = 32 on MI355X / MI350X); the 256 MB is the MALL, not L2
```

**This `saturation` is the coarse fill check, not the quantization tail.** It answers *does the
grid cover the device at all*, and it is **not** `tail_efficiency` — it says nothing about how
much of the *last* wave is wasted. That quantity is `grid_tiles / (waves * CUs)`; mechanism in
`roofline-models.md ## Saturation / wave quantization`, and the rule that it is one-sided — it
can veto a geometry but **cannot rank two configurations** — in
`planning-constants.md ## Tail efficiency is one-sided too`.

No tool assumes a SKU: `hw_budget.py` / `calc_perf.py` / `mem_bw_probe.py` refuse without `--sku`
(or `--arch` for geometry-only subcommands), and a dtype the row does not list is refused, never
priced at FP16.

Every cell above is a published peak (AMD MI350X / MI355X product specifications, June 2025), so
`sku.json` carries `basis: datasheet` for these rows. Three earlier planning values were wrong in the
direction that flatters the opportunity, and are recorded here so they are not re-introduced:

- **FP8 was quoted at 5000 / 5500 TF.** AMD publishes MXFP8 and OCP-FP8 at 4.6 and 5.0 PFLOPS,
  i.e. exactly 2x the FP16 matrix peak on both parts (the same 2x this table shows on CDNA3). The
  old cells were 8.7% and 10% high.
- **FP32 vector was quoted at ~287 TF on BOTH parts.** That came from a scaling rule written as
  "MI300X ratio x MI350 FP16 peak", which MI355X inherited verbatim despite a different FP16 peak
  — so the two rows collided. The rule itself was also wrong: CDNA4 did not keep CDNA3's 1:8
  vector-to-matrix ratio. AMD publishes FP64 vector at 72.1 / 78.6 TF, hence FP32 vector at
  144.2 / 157.3 TF — the old value was nearly 2x high, which halved the FP32 compute floor and
  doubled the apparent prize on any FP32 kernel.
- **MI355X FP4 was quoted at 10100 TF.** GEAK's cell is **10 PF** — 4x the 2.5 PF FP16 cell, the
  same 4x MI350X shows at 9.2 PF. 10.1 is the clock-exact 4 x 2.516 PF; keeping it while FP16 stays
  at the published, rounded 2.5 makes the FP4:FP16 ratio differ between the two gfx950 rows, which is
  exactly the inconsistency the per-arch ratio check exists to catch.

`hw_budget.py --selftest` and `extract_sku.py --check` assert that each dtype:FP16 ratio is constant
across the SKUs of one arch, which is what makes the second and third of these visible; the first was
only ever findable by going back to the published spec, because both cells were wrong together.

Official: [CDNA4 ISA PDF](https://www.amd.com/content/dam/amd/en/documents/instinct-tech-docs/instruction-set-architectures/amd-instinct-cdna4-instruction-set-architecture.pdf).
