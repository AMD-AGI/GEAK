# Optimization gotchas (the reversed-intuition facts)

The ten profile-reading traps where a strong model's *default* move is WRONG. Everything else
in the bound-class tree a frontier model already reasons out unaided; **these it does not** — each
row is a specific "the obvious read is wrong, here's the discriminator." Read this once at the start
of a kernel, and the deep_engineer's closure self-review checks each row before a ceiling stands
(`../method/close.md ## Closure challenge (self-review before a ceiling / keep-baseline / negative close)`). Deep detail is in the
linked file — this table is the high-salience index, not a re-explanation.

| # | Misread (the tempting-but-wrong move) | Discriminator (what actually decides) | Correct move | Source |
|---|---|---|---|---|
| 1 | Low `MfmaUtil` → "occupancy wall", climb the occupancy ladder | **Occupancy adequacy**, not MfmaUtil: ≥2 waves AND not the VGPR/LDS limiter = adequate | If occupancy is ADEQUATE the matrix engine is *under-filled* → **grow the tile** (accept lower occupancy). Only relieve occupancy when waves<2 OR a VGPR/LDS limiter caps it | `bound-class-signals.md ## under-fill vs occupancy` |
| 2 | fp8-scaled matmul reads `MfmaUtil`~0 → "not compute-bound" | On gfx950/CDNA4 the scaled-fp8 pipe does NOT hit the generic MFMA counter — work is in `SQ_INSTS_VALU_MFMA_MOPS_F8` (`mfma_by_dtype.fp8_scaled`) | Read the UNIFIED matrix-engagement test (generic MfmaUtil OR scaled-fp8 pipe engaged). gfx942 fp8 is non-scaled and DOES hit the generic counter — flag is arch-scoped. **On one arch the two calibers still coexist**: an fp8 kernel that deliberately upcasts to bf16 and issues regular MFMA *does* hit the generic counter, so which caliber applies is a per-kernel reading of the matrix op actually issued, never an arch-wide default | `bound-class-signals.md ## Rules` (fp8 scaled-MFMA) |
| 3 | L2 hit low → "locality gap", do XCD/GROUP_SIZE_M remap | Check coalescing too: **L2-low + coalescing-low is a SYMPTOM** of the uncoalesced/small-tile access, not a reuse gap | Coalesce the access / grow the tile — grid remap is INERT here. Only remap when L2 is low AND the access is well-coalesced | `bound-class-signals.md` (L2-hit discriminator rows) |
| 4 | `lgkmcnt(0)` full-drain + low MfmaUtil → "bandwidth-bound", add prefetch/more in-flight | At EQUAL VGPR+AGPR & occupancy vs plain, LOWER MfmaUtil with full-drain `lgkmcnt(0)` and NOT `MemUnitStalled`/`stalled_on_l2` dominant = a **schedule/overlap gap**, not bandwidth | `sub=schedule-overlap`. The move is the **hand-written** overlap in `../tile-programming/pipeline.md` order — (1) register prefetch, (2) authored LDS ring (gfx950 `async_copy` + `commit_group`/`wait_group`; gfx942 sync staging or 32-bit async `order=[1,0]`), (3) `warp_pipeline_stage` + scheduling-model choice (`num_warps>=8`) — then pace it with the per-compile scheduler strategy. On a **Gluon transcription that lost plain's pipeline** that is also how the `lost_pipeline` debt is repaid; re-injecting plain's pipeliner (`reinject_ttgir_pipeliner`) is only a below-parity diagnostic that sizes the debt or a last resort when the hand-written ring cannot reach parity — numbers labelled `injected`, never a win, never on an incumbent Gluon kernel. NOT a ceiling either way | `../tile-programming/pipeline.md ## Where the overlap comes from, and it is not the same question per tier` decides which of those you are in; `bound-class-signals.md` (schedule-overlap row) |
| 5 | Low-precision GEMM (W4A16 / W4A8, or fp8 operands) → "we're at N% of the MFMA roofline", chase MFMA continuity | `asm_loop_audit` VALU% ≫ MFMA%: a **per-element convert on the operand path** dominates and the FLOP roofline has NO axis for it. Int4/int8→bf16 unpack is one form; the commoner AMD form is an **fp8→bf16 upcast feeding regular MFMA**, which looks like a dtype detail and costs a VALU op per element | Bound class is VALU / software-dequant → cheapen or delete the convert (native converter, fold it, or take the native scaled-MFMA path so the operands never widen). Do NOT chase the FLOP/peak MFMA roofline. The upcast form also flips row 2's caliber, so read them together | `bound-class-signals.md` (low-precision op-mix); `../tile-programming/low-precision.md` |
| 6 | Any latency-hiding / prefetch / deeper-pipeline lever "should help" | **Occupancy gates it**: a lever that removes exposed serial-chain latency pays ONLY at low occupancy; on an occupancy-hidden kernel (2+ resident waves) it is neutral-to-negative | Bound-the-win FIRST (disable the targeted dependency, measure the ceiling). If occupancy already hides it, the lever is a wash — spend the round elsewhere | `bound-class-signals.md ## Lever gating laws` (occupancy_gates_latency) |
| 7 | A GEMM throughput-pairing scheduler treated as "just another scheduling knob to try" | It ASSUMES a pure MFMA→MFMA accumulator chain. On VALU-between-matmul (softmax/scale/dequant: attention, MLA, DSA) it emits **invalid IR / a verifier assertion** ("does not dominate all uses"), not a slowdown | Default-SKIP a GEMM throughput-pairing scheduler and the AGPR accumulator hint for VALU-between-matmul ops. Try the stock `coexec` scheduler strategy first for this region class — off by default on gfx950/gfx942 (upstream 3.8.0 enables it automatically only on gfx1250); opt in with `TRITON_HIP_USE_COEXEC_SCHEDULER=1` (process-wide, applies at `num_warps <= 4`) or per compile with `llvm_fn_attrs=[["amdgpu-sched-strategy","coexec"]]` (any `num_warps`), accepted on an assembly diff (`../tile-programming/compiler-contract.md ## What upstream 3.8.0 actually gives you`) —, interleave manually, or author a dependency-preserving pass under sanctioned co-design | `../tile-programming/compiler-contract.md` (a GEMM scheduler asserts here; that file is per-pack and no section in it carries this risk today — read the Tier A / Tier B split) |
| 8 | A compiler/backend pass lever regressed → "the compiler is the ceiling, hand it off" | A **compiler-realized lever exploits structure, it never creates it**: the paired source structure (independent AC/LR/DOT, fitting register budget) must already be in place. A ceiling is valid only after the IR shows the structure is correct yet the pass still clumps/spills | Verify the IR structure FIRST. If the structure isn't there, it's a kernel-structure bug, not a compiler miss — fix the source, don't hand off | `../../skill.md` (the vendored upstream entry: non-negotiable core, compiler-realized lever); `../tile-programming/compiler-contract.md` |
| 9 | `s_nop` in the hot loop → "exposed hazard, add unroll / raise occupancy" | **Three origins the listing cannot tell apart.** (a) compiler-inserted, which is the hazard the tempting read assumes; (b) a couple deliberately placed at a stage head, which is a *phase* lever moving one wave's LDS burst off the other wave's 3-source VALU — contention in the register file, not at the issue port; (c) a bare one ahead of a DPP / `permlane` / cross-lane op, which is an **ISA-mandated wait state** hand-written asm has to supply itself. The discriminator for (c) is the NEXT instruction | Identify the origin before acting. For (a) the usual hazard moves apply. For (b) phase effects are **non-monotone — sweep, do not bisect**. For (c) **deleting it is a correctness bug**: the required counts are in `isa-mechanisms.md` (CDNA4 wait-state table) and the packaged ISA facts | `../tile-programming/llir-codesign.md ## Phase pacing: moving a burst instead of removing work`; `isa-mechanisms.md` |
| 10 | A schedule tool changed nothing → "we are at the schedule ceiling" | **Two silent skips come first.** (a) *Applicability*: is the loop's matrix shape in the tool's cost model? An unpriced shape costs 0, so the solver discards the whole region. (b) *Satisfiability*: was the declaration achievable? One op that never issues makes the solver abandon the region. Both leave the assembly looking un-scheduled, which is exactly what a real ceiling looks like | Rule out both before recording a ceiling: confirm the shape is modelled and the declaration is satisfiable, and check the window model is calibrated for this target. Only then is "no change" evidence about the schedule | `../tile-programming/llir-codesign.md ## Applicability gate: shapes the tool does not model`; same file `## Declaring the interleave` |

Every row is calibrated on gfx950 (CDNA4) first. **gfx942 downgrade note (rows 2, 4, 7):** the
arch-scoping matters — fp8 is non-scaled (FNUZ) on gfx942 so row 2's caliber question does not
arise; row 4's authored ring downgrades to sync staging; and the GEMM-only compiler knobs carry
version-3 caveats. When the target is gfx942 read `cdna3-gfx942.md` before trusting a
gfx950-calibrated read.
