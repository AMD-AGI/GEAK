# Derive the split-KV decode launch shape from a constant-byte tile and a WG/CU fill target
- lever: Replace the constant tile/segment limits of a split-KV decode attention with two host formulas — a KV tile sized by constant BYTES (tile x head_size ~= 8192 elements holds across head_size 64/128/256/512) and a segment count chosen to fill 4-6 workgroups per CU — plus one wrapper-computed constexpr "every query length is 1" flag that lets the partitioned body drop its sequence search, its row masks and its surplus query blocks. Treat that exact-fill flag as the first move and the launch-meta table (num_stages / waves_per_eu, per path) as a re-sweep on top of it: the block-count upper bound such wrappers use launches 12-50% more programs than do work, and each dead program also carries the binary search over the varlen offset array and its dependent scalar-load chain.
- apply: All of it is host-side plus constexpr: clamp(TILE_ELEMS//head_size, 16, 128) for the tile, wg_target = cu_count x wg_per_cu for the split, and a boolean derived from (max query len == 1 and rows == num_seqs) passed as tl.constexpr. The gather path for tile != page block already exists in most such kernels, so raising the tile is a config change, not a rewrite.
- stack: total 1.71x geomean isolated (director-verified) = four pieces compounded, incremental in landing order
  - 1. constant-byte tile + unclamped segment floor — 1.38x standalone (round 1, verified) — largest single lever
  - 2. decode-exact constexpr grid + mask-free body — 1.18x standalone (round 1, verified), about two thirds of it the exact grid alone; roughly doubles in value once (1) has landed
  - 3. fill target raised to 4 WG/CU (2.5 when head_size >= 512) — cumulative 1.61x weighted (round 2, verified); took two cases from 1.00 to 2.00 waves/SIMD
  - 4. cache hint keyed on KV element width — +~0.8% weighted at integrate, all of it the single fp8-KV case at -8.9% latency
  - note: a fifth (memory) direction contributed nothing; (2)'s standalone ceiling and its stacked value differ, so the split above is not additive.
  - second lane, total 1.84x isolated (director-verified) = 1.61x from an earlier grid/tile round, then +12% from the exact-fill decode grid alone (round 2, verified) — uniformly -10% to -15% on all four cases, the signature of a per-launch FIXED cost leaving — then +1.1% at integrate from re-sweeping the launch table on top of the new grid; a reduce-shrinking direction regressed below the incumbent and was excluded.
- verify: Confirm the launched workgroup count and waves/SIMD actually moved per shape, sweep the fill target so you see the plateau rather than a point (2.5/4/5/6/8/12 measured 1.425/1.505/1.502/1.499/1.365/1.363 weighted — flat 4-6, collapsing past 8), and re-run oracle parity on both dispatch paths.
- pitfall: raising the fill target changed nothing on the smallest head_size → tile granularity silently caps the segment count (next_pow2(ceil(max_kv_len / tile)) clamps it) → sweep tile size and segment count jointly, not one at a time.
head_size >= 512 lost ~10% when split further and was blamed on register pressure → VGPR count was low with zero scratch, so registers were not the constraint; the fp32 segment scratch scales as segments x head_size → carve that head_size out of the raise and re-price it after narrowing the scratch dtype.
two rounds of body surgery on the reduce dispatch (deleting its serial sequence search, folding exponentials, lowering waves_per_eu) left its p50 within 1% of baseline → its cost is launch width at 0.25-0.75 waves/SIMD, not work and not a dependency chain → spend the round on its grid width; the one gain that did land there was a constexpr promotion deleting a 6-deep dependent scalar-load chain ahead of every address.
an L1-bypass cache hint that helped bf16 KV inverted on the fp8-KV case → its sign tracks KV element width → key it on the cache dtype rather than on shape.
one direction "verified" at exactly the previous round's cumulative number → every knob it added was env-gated and defaulted to canonical behaviour, so it measured a no-op → diff a lane's workspace against canonical before crediting it.
a ~15-arm launch-meta sweep in which every windowed arm landed within noise of stock was written up as "that axis is dead", and the non-result was then baked into the config table as a comment reading like evidence → the tuning override was read only on the branch where the attention window was disabled, so the windowed arms all re-measured the stock config → prove the knob is live twice before crediting any arm, positive or negative (print the tuple the wrapper actually chose, and run a deliberately-bad arm that visibly moves the number); once live, the same sweep paid ~+3% per sliding case, and a sweep whose arms all sit within noise of stock is evidence about the KNOB, not the axis.
a grid/fill change silently staled the launch table → the previous optimum had been tuned against the old program count → sequence the rounds so the grid change lands first and the table is re-swept on top of it (that move went num_stages 2 -> 3 with waves_per_eu 2, +1.9%/+4.3% per full-attention case); waves_per_eu=2 was the one sharply-peaked winner on both the 2D and the split-KV path, while deeper-pipeline and wider-tile arms lost 6-85%, so the payoff is a second resident wave rather than deeper prefetch.
a 2-way KV split on the windowed path netted -5% → a plain sequence-length segmentation left segment 0 entirely empty once the window pruned the early tiles, so it bought no parallelism, and the extra reduce dispatch cost more than the attention kernel saved at 86% of roof → segment window-aware, and price the split against the reduce dispatch it adds before funding it.
the workspace loader only reloaded the main kernel file, so edits to its helper module were silently ignored and the installed package's copy was called instead (surfacing as an argument-count mismatch) → inline anything the kernel needs from a helper module into the file the loader actually reloads, and confirm the edit is the code that ran.
- caution: also verify the box is idle before each arm — runs that slipped past the idleness gate while a foreign tenant held neighbouring GPUs read 2-30x inflated, and an identical binary drifts 2-5% between sessions (cross-batch drift of ~1.7% was visible between identical configs here), so headline numbers want paired same-session medians of >=3 interleaved reps with the anchor re-measured in your own workspace; also verify each accepted candidate still reads its full hand-modelled KV working set (read-request counter x cache-line width matched the model to <0.6% before and after here), which is the cheap way to catch a "speedup" that stopped reading KV rather than going faster; and also verify the roofline denominator is a read-only streaming measurement rather than a copy measurement on a read-dominated kernel — the copy denominator here understated the roof enough to make one case read as an impossible fraction above peak.
